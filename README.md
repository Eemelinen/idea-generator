# Ideaforge

A local business-idea validator for founders in Rääkkylä / North Karelia, Finland. It runs on Claude Code with a Claude Max subscription and uses no paid third-party services.

You type an idea. Ideaforge researches it across ten feasibility dimensions with parallel subagents, verifies every quoted claim against its source, scores the idea in Python and writes an evidence-backed report. If you ask, it also runs a structured debate that tries to improve the plan.

## Setup

1. Install [uv](https://docs.astral.sh/uv/). uv downloads Python 3.12 for the project.
2. `uv sync`
3. `uv run python scripts/gen_agents.py`
4. `uv run pytest`

If downloads fail with `invalid peer certificate: UnknownIssuer`, something on the machine (antivirus or a proxy) is intercepting TLS. `pyproject.toml` already sets `[tool.uv] system-certs = true`, so commands run inside the project use the system certificate store. Commands run outside the project need `--system-certs`.

## Usage

Inside Claude Code, in this directory:

```
/validate [--preset economy|standard|deep] <idea text>   # stages 0–3 (intake → claim verification)
/validate <run_id>           # resume a run: skips completed stages and research dimensions
/validate --from <run_id> [<revised idea text>]   # a new version <run_id>-vN; the old run and report stay unchanged
/research <run_id>           # stages 1–3 of an existing run
/synthesize <run_id>         # stage 5: proposed scores and risks, the score sheet and verdict, the report
/status [run_id]
/status <run_id> --review     # score the report's sections 1–5 (stored in the reviews table)
/status --reviews            # review-score trend across prompt and model versions
/status --diff <run_a> <run_b>   # compare two score sheets: dimensions, verdict, kill triggers
/debate <run_id>             # Phase 4
/eval [--limit N] [--fresh]  # Phase 5: the golden set, one idea at a time, then eval_check.py
```

Status: Phase 1 (the skeleton) is done; of Phase 2, the recorded Finnish API fixtures (`uv run python scripts/record_fixtures.py`, run by hand with network; `tests/fixtures/api/`), the StatFin/Luke PxWeb client (`uv run python -m ideaforge.fi.pxweb search|meta|get`), the PRH company search and the Eurostat client (`uv run python -m ideaforge.fi.prh search`, `uv run python -m ideaforge.fi.eurostat get`), the research validator, the drafted production research briefs (search strategy, Finnish search terms and `fi` tools per dimension), the optional claim-extractor pass (`uv run python scripts/extract_claims.py <run_id>` lists the cited sentences no candidate claim covers; only then does stage 3 launch the `claim-extractor` agent), claim verification (`uv run python scripts/verify_claims.py <run_id>`, which also re-runs the query behind every `fi` API claim and marks conflicting figures, `03_claims/conflicts.json`, when two sources give different figures for the same measure; `--conflicts-only` recomputes them from an existing ledger without fetching), the usage report, basic `/status`, the stage state machine and the `/validate` and `/research` skills for stages 0–3 are built; of Phase 3, scoring, unit economics, `/synthesize` (stage 5), the report and versioning (`meta.json`, `/validate --from`) are built; of Phase 4, the `/debate` skill with its persona and judge prompts, debate anonymization, rebuttal validation, mini-research, the convergence check, the conformity flag and the revised plan (the first live debate is still to come); of Phase 5, the golden-set schema, `scripts/eval_check.py` and the `/eval` skill (the golden set itself is IF-501), back-test mode (`--as-of`), the preset budget lines in the research briefs (`scripts/research_brief.py`), review scores and `/status --diff`; of Phase 6, the web app shell with the runs dashboard, the schema migrations and `python -m ideaforge.db backup`, the run page (stages, idea, claims, scores, economics, report, usage, files), its debate and review tabs, the persistent job queue with its headless worker (`python -m ideaforge.jobs`) and pipeline control from the UI (new ideas and versions, run actions, eval, the jobs page with its log tail). See `docs/TICKETS.md` for what comes next.

- `uv run python scripts/run_stage.py <run_id> <stage> --begin|--finish|--insufficient-data` moves one stage through `pending → running → done | failed` (`insufficient_data` for a research dimension that failed twice); a stage is done only when its output file(s) exist and validate. `run_stage.py <run_id> --resume` makes the run active for the hooks, repairs the stages a crash left `running` and prints the stages to run next (`--next` prints them without repairing).
- `uv run python scripts/usage_report.py <run_id>`: tool calls, searches, fetches and approximate tokens per stage and per agent, plus the run's `BUDGET_EXCEEDED_*` markers.
- `/synthesize <run_id>`: `uv run python scripts/synthesis_input.py <run_id>` writes `04_synthesis_input.json` (the spec, the verified and conflict claims, the rubric), the `synthesizer` subagent reads only that file and writes `04_scores_proposed.json` (scores, citations, unit-economics inputs) and `04_risks.json`, and `uv run python scripts/score_run.py <run_id>` drops unverified citations, applies the caps, kill triggers and unit economics and writes `04_scores.json` and the `scores` rows. Then `uv run python scripts/render_report.py <run_id>` writes the immutable `05_report.md`: verdict and why, score table with cap labels, kill triggers, unit economics and sensitivity, dimension sections, Finland funding fit (each item backed by a verified official-source claim or shown as a gap), Rääkkylä notes, risk register, a starttiraha business-plan draft (liiketoimintasuunnitelma skeleton and kannattavuuslaskelma, in `config/report.yaml: business_plan_language`, every figure traced to claim ids or marked as an assumption), sources and usage. It never overwrites an existing report.
- `uv run python scripts/new_run.py --from <run_id> [<idea text>]` (what `/validate --from` runs) creates the next version `<run_id>-vN` with its own directory, linked through `idea_versions.parent`; the idea text, budget preset and `--as-of` date default to the parent's and the parent run is never touched. Every run's `meta.json` records the repository HEAD, the last commit that changed `config/`, `prompts/` or `agent_templates/` (and whether they had uncommitted changes), the `config/models.yaml` roles, the Claude Code version (`claude --version`), the idea version and `created_at` / `updated_at` (refreshed by each stage transition).
- `/debate <run_id>` runs the debate on a run with a report and resumes per round (`uv run python -m ideaforge.debate status <run_id>` prints the next step). Each persona sees the report and its own evidence subset, `debate/evidence/<role>.json` (`uv run python -m ideaforge.debate evidence <run_id>`). A mini-research request becomes a task (`uv run python -m ideaforge.mini_research open <run_id> <round>`, at most `max_mini_research_tasks` per debate) for the dimension's research agent, which writes `02_research/mini-<n>-<dim>.md`; `mini_research finish` validates it and `uv run python scripts/verify_claims.py <run_id> --only mini-<n>-<dim>` verifies only its claims, which every persona gets next round. Its building blocks: `uv run python -m ideaforge.debate anonymize <run_id> <round>` maps the five personas to P1…P5 with a seed stored in the `debates` table and `debate/.mapping.json` (never shown to personas or the judge) and writes `debate/round<N>/positions_anon.json` without role names. `uv run python scripts/debate_validate.py <run_id> <round>` rejects a stance change without a new claim id or a computation, a disagree without a claim id or an evidence gap, unknown or unverified claim ids and a second mini-research request in a round, writes the reasons to `debate/round<N>/REJECTED_<role>` and records each turn in `debate_turns` (exit 2 when a persona must be re-prompted). `uv run python scripts/debate_converged.py <run_id> <round>` exits 0 when the debate should stop: no new claim id and no moved proposal in the round, the judge's interim projected scores (`debate/round<N>/interim_scores.json`) moved less than `convergence_score_delta` on every dimension, or the preset's `max_rounds` is reached (exit 2: run another round). After the judge, `uv run python scripts/render_report.py <run_id> --debate` checks that every accepted change cites verified claims, recomputes `conformity_flag` into `debate/verdict.json` (≥ 4 of 5 personas backing one change while no new claim id entered), writes the immutable `debate/revised_plan.md` (a diff against `05_report.md`, the assumption register and at least five experiments ordered by info value per euro) and stores the `assumptions` and `experiments` tables.
- `/eval [--limit N] [--fresh]` runs each golden idea in `tests/golden/*.yaml` (schema `GoldenIdea`: the idea, `expected_verdicts`, 2–3 `must_find` facts with source URLs and optional keywords) through stages 0–5, sequentially, reusing a finished run and resuming an unfinished one unless `--fresh`. `uv run python scripts/eval_check.py [--limit N]` then checks each idea's newest run (found by its idea text): the verdict is one of `expected_verdicts`, every must-find fact is found by a verified claim (same source URL, or every keyword in its statement or quote) and the score sheet cites no claim that is not verified; it prints a Markdown summary table and `passed: X of N` (exit 2 when one fails). `--plan` lists the golden ideas and their runs without the answer key.
- `/status` (`uv run python scripts/status.py [run_id] [--limit N]`): the recent runs and their stages; with a run id, its stages, claims per dimension by verification state, kill flags fired, validation and budget markers and the usage summary. `/status <run_id> --review` lists the sections of the run's `05_report.md`, asks you to score each 1–5 (an optional note each) and stores them in the `reviews` table (`scripts/status.py <run_id> --review verdict=4 'risks=2:too generic' …`); `/status --reviews` shows the mean score per section for each prompt/config and model version from the runs' `meta.json`, so drift after a prompt or model change shows. `/status --diff <run_a> <run_b>` compares two runs' `04_scores.json`: final score per dimension, weighted total, verdict, kill triggers fired, and the config and model changes between the runs.
- `/validate --as-of YYYY-MM-DD <idea text>` is a back-test: the research briefs carry a header that allows only sources published on or before that date, and `verify_claims.py` marks a claim whose `published_date` is later `unverified` with the flag `after_as_of` (without fetching it). An undated claim is not rejected. `uv run python scripts/research_brief.py <run_id> <dim>` prints the lines every research brief gets: the run's budget line and, in a back-test, that header.

## Web UI

A local web UI (Phase 6, D-008) has the runs dashboard, the run page with its debate and review tabs, the review trend and run comparison, pipeline control (new ideas, run actions, eval, the jobs page) and the settings editor.

- **Start**: `uv run python -m ideaforge.web [--port 8765]`, then open <http://127.0.0.1:8765/>. **Stop**: Ctrl+C in that terminal; a job still running is stopped and marked `failed` / `interrupted` (retry it later, the stages resume).
- **Local only**: the server always binds to `127.0.0.1` and has no login. Never expose it on a network interface or through a tunnel. A form post (anything that changes state) is refused unless it comes from the UI itself (a loopback host name and the same origin), so another web page open in the browser cannot start jobs.
- **Runs dashboard**: every run, newest first, grouped by idea (versions made with `--from` under their idea, each with its parent), with its stage progress, verdict and weighted total once scored, debate state, preset, as-of date and approximate usage. Filter by verdict (`none` = not scored) or idea. The figures come from the same functions as `/status`. A banner warns when a `runs/<run_id>/` directory has no database row or a database row has no directory.
- **Run page** (`/runs/<run_id>`, linked from the dashboard), read-only, with tabs: **Stages** (status, attempts and times per stage, and the full text of every `BUDGET_EXCEEDED_*` / `VALIDATION_*` marker), **Idea** (`idea.md`, the spec with its clarifications, the research plan per dimension), **Claims** (the ledger from `03_claims/verified.json`, or the claims table before stage 3 has written it, filterable by dimension, verification state, source type and flag, with each claim's source link and quote, and the conflict groups in preference order), **Scores** (proposed and final score, cap reason, status and justification per dimension with claim links, weighted total, verdict, kill triggers fired, flagged and overridden), **Economics** (unit economics, missing inputs, the sensitivity table, the input claims per role), **Report** (`05_report.md` as HTML, with any HTML in it escaped, and a download link), **Debate** (the next step as `python -m ideaforge.debate status` names it; per round the anonymized positions and rebuttals as the judge saw them, rejected and re-prompted turns with their reasons, mini-research tasks and their claims, and the judge's interim scores; then the verdict with its accepted and rejected changes, a banner when the computed conformity flag is raised, the assumption register, the experiments by info value per cost and `debate/revised_plan.md`; personas appear as P-ids until `debate/verdict.json` exists), **Review** (a form that scores each report section 1–5 with an optional note and stores it like `/status <run_id> --review`; a section left blank keeps its score), **Usage** (per stage and per agent, as `usage_report.py`) and **Files** (every file under `runs/<run_id>/`, viewable and downloadable; `..`, absolute paths and symlinks get a 404, and `debate/.mapping.json` stays hidden until the debate verdict exists). A tab whose stage has not run says so.
- **New idea** (`/new`): the idea text, the founder constraints (goal, capital, hours and skills), the scope (business mode `local`, `online` or `hybrid`; the target markets, nearest first; the base location: municipality and region with their optional Statistics Finland codes, nearby towns, official domains and an optional Leader group), all prefilled from `config/founder.yaml` (Rääkkylä / `local` unless changed on the Settings page), the budget preset, an optional as-of date, up to five clarifying answers, optional kill-trigger overrides and how far to run (validate; validate + synthesize; validate + synthesize + debate). The form becomes the run's `intake.json`, so the headless `/validate` asks nothing; a form with a problem is shown again with every reason and creates nothing. Submitting creates the run and queues the job chain, then opens the first job.
- **Run actions**: the run page offers only what the run's state allows: **Resume validate** while stages 0–3 are incomplete, **Synthesize** once they are complete and until the report exists, **Debate** once the report exists and until `debate/revised_plan.md` does, and **New version** (a form like New idea, prefilled from the run's spec, scope included, that creates the next version with `--from`). Nothing is offered while a job for the run is queued or running; the server refuses the same cases. The dashboard has **Run eval** (optional `--limit`, `--fresh`), refused while an eval job is open.
- **Jobs** (`/jobs`): every job, newest first, with kind, run, status, reason and duration, and cancel or retry. A job's page shows its command, its chain and a live log tail (the page polls for the new bytes every 2 s and reloads when the job ends). The server runs the job worker in the background from start to stop (one at a time, as `python -m ideaforge.jobs worker`); while `.ideaforge-dev` exists every page shows a banner that the worker is blocked, and queued jobs wait. With a separate CLI worker already running, the server's worker stays off and says so; the CLI worker runs the UI's jobs.
- **Reviews** (`/reviews`): the review-score trend by prompt/config and model version, the same table as `/status --reviews`. **Compare** (`/compare`): pick any two runs (versions of one idea, or any two) for the per-dimension final scores, weighted total, verdict and kill triggers, the same diff as `/status --diff`.
- **Settings** (`/settings`): one page per pipeline config file (`models`, `budget`, `founder`, `report`, `rubric`, `domains`, `finland`), each a form built from its `ideaforge.config` model (dropdowns for model aliases, presets, goals, languages and evidence rules; lists one item per line; the file's own comments as help) plus the raw YAML as a fallback for what the form cannot change (adding or removing a preset, dimension, hint or rule). A save is validated first; an invalid one changes nothing and lists the errors. A form save keeps the file's comments, key order and layout (`ruamel.yaml` round-trip; a changed number is written as Python spells it, `0.10` → `0.1`). Saving `models`, `budget`, `rubric` or `domains` regenerates `.claude/agents/` (`scripts/gen_agents.py`, its output is shown); if that fails, the file is restored. The `harness_*` model roles are read-only (they must match `harness.config.json`, which the UI does not edit). Saving is refused while a job is running, because a run snapshots the settings at its start. Every save is listed under **History** with its diff and a **Revert**, which is itself a validated save. Settings changed here make `config/` differ from git, so commit them when they should stay.
- **Database upkeep**: `db.init()` (run by `new_run.py` and at UI start) migrates the database to the latest `schema_version`, keeping every row. `uv run python -m ideaforge.db backup [--to <dir>]` writes a consistent copy to `backups/ideaforge-<UTC timestamp>.db` (gitignored), safe while the pipeline is writing; `uv run python -m ideaforge.db init` prints the schema version. To restore, stop everything that uses the database and copy a backup over `ideaforge.db` (delete `ideaforge.db-wal` and `ideaforge.db-shm` first).

## Headless runs (job queue)

`uv run python -m ideaforge.jobs` keeps pipeline jobs in the `jobs` table and runs them without anyone at the keyboard (IF-604; the UI's New idea form, run actions and Jobs page, IF-607, drive the same queue).

```
uv run python -m ideaforge.jobs enqueue validate --idea '<idea text>' --intake '<json>' [--preset economy] [--as-of YYYY-MM-DD] [--then synthesize --then debate]
uv run python -m ideaforge.jobs enqueue synthesize|research|validate|debate --run <run_id> [--then <kind> …]
uv run python -m ideaforge.jobs enqueue eval [--args '{"limit": 3, "fresh": false}']
uv run python -m ideaforge.jobs list | show <job_id> | cancel <job_id> | retry <job_id>
uv run python -m ideaforge.jobs worker [--once]
```

- **New ideas**: `enqueue validate --idea … --intake …` runs `scripts/new_run.py --intake` first, so the job knows its run id. The intake JSON (schema `Intake`: `goal`, `capital_eur`, `hours_per_week`, optional `skills` (default `config/founder.yaml`'s), `geography`, `business_mode`, `base_location` (both default to Rääkkylä / `local`), up to 5 free-text `answers` as `{question, answer}`, `kill_trigger_overrides`) is written to `runs/<run_id>/intake.json`; `/validate`'s stage 0 builds the spec from it and asks no questions, and the plan is not held for approval. An invalid intake creates neither a run nor a job.
- **Worker**: takes the oldest queued job and runs one at a time as `claude -p "/<kind> <run_id>" --model <roles.orchestrator> --output-format stream-json --verbose` in the project root; the output goes to `runs/.jobs/<job_id>.log`. Exit 0 → `done`; otherwise `failed` with the reason `usage_limit` (the session reported a usage or rate limit) or `exit <code>`. `--then` jobs wait for their predecessor and are cancelled when it fails or is cancelled. `--once` runs at most one job; without it the worker polls until Ctrl+C (which stops the running job too, marking it `interrupted`). `IDEAFORGE_CLAUDE_BIN` replaces the `claude` binary.
- **Strict guard**: the worker refuses to start while `.ideaforge-dev` exists and removes `HARNESS_LOOP` from the job's environment, so every job runs under the strict pipeline guard. Only one worker runs at a time (`runs/.jobs/worker.pid`).
- **Cancel, retry, restart**: `cancel` drops a queued job or stops a running one (SIGTERM, then SIGKILL after 10 s) and cancels its chain. `retry` queues a finished job again with the same run and arguments, plus the chained jobs its end cancelled; the stages resume, so the run continues where it stopped. A job left `running` by a crash or restart becomes `failed` with the reason `interrupted` when the worker starts again.

## Usage limits, presets and model downgrades

Ideaforge runs on a Claude Max subscription and nothing else, so the limit that matters is the subscription's usage limit, not money.

- **Before a batch** (several `/validate` runs, `/eval`, a debate), check `/usage` in Claude Code. Run heavy stages one idea at a time; `/eval` is sequential by design. After every stage the skills print `uv run python scripts/usage_report.py <run_id>`.
- **Headless jobs** run strictly one at a time. A job stopped by a usage limit is `failed` with the reason `usage_limit` and its chain is cancelled; once the limit resets, `uv run python -m ideaforge.jobs retry <job_id>` continues the run from the stage it stopped in.
- **Presets** (`config/budget.yaml`, chosen with `/validate --preset economy|standard|deep`; the default is `standard`). A new version made with `--from` keeps its parent's preset unless `--preset` is given.

  | Preset     | Searches / fetches per research agent | Words | Killcause searches / fetches | Debate rounds | Mini-research tasks |
  | ---------- | ------------------------------------- | ----- | ---------------------------- | ------------- | ------------------- |
  | `economy`  | 6 / 6                                 | 1000  | 8 / 6                        | 2             | 1                   |
  | `standard` | 8 / 8                                 | 1200  | 10 / 8                       | 3             | 3                   |
  | `deep`     | 12 / 12                               | 1600  | 14 / 12                      | 3             | 3                   |

  The generated agent files carry the default preset's numbers and name no place, so the orchestrator pastes the run's scope lines (business mode, base location with its codes, target markets and the mode's guidance, from `00_spec.json`) and budget line from `research_brief.py` into every research brief, and the scope lines alone (`research_brief.py <run_id> --scope`) into every debate persona's brief. The usage hook counts each research agent's `WebSearch` and `WebFetch` calls against the run's preset (from `meta.json`) and writes `runs/<run_id>/BUDGET_EXCEEDED_<agent>` when one goes over (an economy research agent at its 7th search); the research validator applies the preset's word limit.

- **Model downgrade order** (`config/models.yaml`, every role defaults to `opus`): `claim_extractor` (→ `haiku`) first, then `debate_persona` (→ `sonnet`), then `research_subagent`. Keep `synthesizer` and `debate_judge` on `opus` longest.
- **Downgrade procedure**: edit the role in `config/models.yaml` (never a model in an agent file) → `uv run python scripts/gen_agents.py` → `/eval --limit 3` (3 golden ideas) → compare the score sheets with the previous model's runs with `/status --diff <old_run> <new_run>`. Every run's `meta.json` records the roles it ran with.
- **Fable models** count against the weekly limit faster and are capped at 50 % of it. Use them only through `/model`, and only for the synthesizer or the judge on ideas that matter; never put them in `config/models.yaml`.

## Development

The project's hooks block writes outside `runs/` and `cache/` and allow only a short list of shell commands. To work on the code itself, create an empty `.ideaforge-dev` file at the project root (it is gitignored). Subagents are always held to the strict rules.

After editing `config/models.yaml`, `agent_templates/` or `prompts/`, run `uv run python scripts/gen_agents.py`. The tests fail if the generated agent files are stale.

The remaining work is built with an agent harness: one feature per Claude Code session, verified by scripts before it counts as done. You need Node 24 (`.nvmrc`) with pnpm, plus uv, and on Windows Git Bash. `uv`, `claude` and `gh` must be on `PATH`.

- `./init.sh` installs both toolchains and runs the L1 check, `pnpm check`.
- In Claude Code: `/harness:clock-in` picks and activates the next feature, `/harness:verify-feature F-NNN` runs its checks, and `/harness:clock-out` commits. The skills, hooks and loop come from the shared harness ([Eemelinen/harness](https://github.com/Eemelinen/harness)), configured in `harness.config.json`.
- `pnpm harness:feature list` shows the queue (`feature_list.json`; tickets in `docs/TICKETS.md`).
- `pnpm harness:loop --once` runs one ready feature unattended in its own worktree and opens a PR.

The session loop is described in [AGENTS.md](AGENTS.md) and the driver in [docs/harness/README.md](docs/harness/README.md).
